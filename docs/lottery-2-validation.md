# 抽奖 2.0：根因与验收

## 来源与基线

- [Issue #2](https://github.com/ScryAbu/Annual-Lucky-Draw/issues/2)：2026-05-15 提出超过 100 人带照片闪烁，并要求控制最终中奖者字段。核查时仍 open、0 评论、无关闭时间。
- 分析基线：`a2691597e502099f493539e7ac41a9b93a3a8bee`（远端 main，包版本 1.2.2）。README 中的“流畅无闪烁”不是测试结论。
- 这里区分代码中能直接证明的触发链与实际运行验证；未声称在所有 GPU、人数规模和系统上都达到固定帧率。

## 闪烁的具体原因与最小修复

旧 `src/hooks/useLotteryEngine.ts` 在每 100ms 的 interval 中更新 `rollingDisplays`；该状态并未被球体使用，但 hook 订阅整个 store，使页面每次更新都重渲染。

旧 `src/pages/LotteryPage.tsx` 每次调用 `getAvailablePool()`，对默认排除中奖者的池使用 filter，得到新的数组引用。旧 `src/3d/LotterySphere.tsx` 的 `displayEmployees` 依赖这个数组，并在超过 60 人时执行随机 sort + slice(0,60)。因此 150 人时，10 次/秒地更换成员及位置，React 按人员 key 反复卸载/挂载卡片；有照片的卡片等待异步 Image.onload 才 render，不加载完成就返回 null。两条路径合在一起，直接产生不断消失、出现和跳位的效果。

旧纹理没有 dispose，异步完成时已卸载的纹理也未回收；透明平面以 0.95 不透明度参与深度写入，重叠排序进一步影响观感。前者是能直接证明的资源泄漏，后者是渲染策略风险，不将它冒充报告的唯一原因。不存在可证实的“Three.js 超过 100 人限制”，实际触发阈值是旧代码的 60 人分支。

最小补丁可以仅做：① memoize 可用池；②删除未用于球体的 100ms 状态更新，或缩小订阅；③展示名单稳定，不以 render 重新抽样；④照片先显示文字占位，处理失败和取消并 dispose 纹理。2.0 在此基础上加入固定顺序分页及完整字段控制。

现在 `LotterySphere` 使用面向相机的 Sprite，背景不透明、正常深度测试，避免透明卡片排序。每张卡片只拥有一张 CanvasTexture；异步照片完成是在同一画布上绘制。纹理绑定后明确更新材质 shader，清理会解除引用并 dispose，避免初次绑定空 map 的白卡问题。

## 其他可直接确认的问题

- **3 人上下不动/1 人异常**：旧位置公式 `i/(count-1)` 把首尾放在 y 轴两极，且 1 人时除零；改为 `(i+0.5)/count` 避开两极。
- **动画与中奖人不一致**：旧场景只显示随机 60 人；写入中奖状态后又把中奖人从 availablePool 排除。现在开始时冻结全池，停止只抽一次并原子保存，场景突出显示同一组中奖人，随后弹窗复用这组人员。
- **抽取人数**：旧空格键没有传 drawCount；现在鼠标、键盘共用入口，人数变化自动限制到剩余名额。
- **随机公平性**：旧 `sort(() => Math.random()-0.5)` 不是均匀洗牌；常规模式改为 Web Crypto 随机数、逐次无放回抽样。权重模式按剩余权重区间抽取。
- **批量持久化**：旧逐人调用 clear + bulkAdd，异步交错可能损坏列表；中奖人员与奖项现在在一次 Dexie 事务中保存，失败时不揭晓结果。
- **字段开关不生效**：旧 WinnerDisplay 写死工号/部门，球体又独立生成纹理；现在统一 themeStore.displayOptions。

## 反馈逐项对应

| 反馈 | 对应实现与验收 |
|---|---|
| 1 动画与中奖人不一致 | useLotteryEngine + commitWinners；固定本轮结果，冻结池，场景/弹窗/数据库一致 |
| 2 投屏、转速、3 人几乎不动 | PresentationControls + Electron screen API；速度滑块；半步球面分布 |
| 3 人多显示不全 | 180 人以内全部呈现；超过后每 8 秒顺序翻页，一轮覆盖全名单，资格不受分页限制 |
| 4 工号非必填 | Excel 与手动表单均支持无工号；assignMissingIds 生成独立号码，同名不合并 |
| 5 框里显示工号而非无关数字 | 卡片直接绘制真实 id；只号码预设没有渲染序号 |
| 6 照片、部门都关，只显示姓名 | 四项独立开关 + 只姓名预设，三个模式共用 |
| 7 增加中奖概率 | 人员权重 1–100；需显式选择权重模式，大屏可见；默认等概率 |
| 8 配置跨电脑保存 | 完整 JSON 备份，含照片/奖项/记录/主题/音乐/权重/指定中奖；先校验后事务恢复 |
| 9 Mac 安装包 | electron-builder 输出 x64/arm64 DMG 和 ZIP；macOS CI 构建；签名、公证和实机安装单独验收 |
| 10 150 人闪烁 | 稳定卡片、去掉高频换样、同纹理解码、释放纹理；GPU 上传计数实测 |
| 11 只显示序号/号码 | Excel 导入只有号码的一列，或手动添加号码；只号码预设隐藏照片、姓名、部门 |
| 12 中奖页工号部门关不掉 | WinnerDisplay、轮盘、终极大奖统一字段选项 |

旧版指定中奖配置会迁移保留，但入口改成可见按钮，并在大屏显示启用状态。常规权重与“终极大奖积分”互相独立；不把增加概率描述为保证中奖。

### 现场人工验收

1. 150 人带照片，分别连续滚动 60 秒、重复抽取 10 轮。观察照片不以 100ms 频率换人/闪现，GPU 资源随卸载回收，无持续增长。
2. 1、2、3 人分别开始和停止；所有人都运动，结果真实对应，最后一人仍可抽取。
3. 1000 人等待 6 页（每页 8 秒），核对每人均在一轮出现；页面显示人数与总池一致。抽取覆盖全部资格池。
4. 在三种抽奖模式分别验证“只姓名”“只号码”、照片开部门关、照片关部门开；结果、滚动卡片均尊重设置。
5. 把带照片、背景和音乐的完整配置导出到另一台电脑；核对主题、名单、奖项、记录及权重。尝试损坏 JSON，旧活动不得被替换。
6. 连接扩展屏，选择显示器并全屏；断开显示器后重新选择，检查错误可见；在 Windows 与 Mac 分别检查快捷键及屏幕缩放。
7. Mac 在 Intel / Apple Silicon 上各安装对应包并离线抽奖，检查系统签名、公证状态。CI 构建成功不替代这个步骤。

## 当前验证边界

本机可验证 Windows 构建、真实 Chrome 渲染与 IndexedDB；物理外接屏、Mac 实机以及 Apple 签名/公证不属于已完成的本机实测。没有对 1000 人同时显示 1000 张大纹理的性能作保证；采用分页控制资源数量。开发依赖的 Three.js 多实例提示来自测试渲染器的 CJS/ESM 加载，浏览器运行时无未捕获异常，以实际 GPU 资源和截图验收。
